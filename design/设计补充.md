# 设计补充：解说词生成如何复用 deerflow_simple

## 一、三个核心结论

1. **是否同一套 agent 系统？** —— 共用**同一套装配机制**（`create_agent` 原语 + LangGraph ReAct + 同一 `create_chat_model` + 同一 config），但实例化成**两个独立 graph**，不是同一个对象。
2. **需不需要裁剪？** —— **框架源码一行不改**；裁剪发生在**装配传参的选择**上，而非改 deerflow_simple 代码。
3. **lead_agent 如何委派？** —— 通过 `generate_narration` 工具（tool-as-workflow-entry），工具内部 `invoke` 一个 NarrationAgent 并同步返回，**不是** LangGraph 子图嵌套。

## 二、两个 agent 的精确关系

deerflow_simple 现有的 `lead_agent` 与 `SubagentExecutor` 即先例：**同一套框架，两个 `create_agent` 实例，靠工具边界连接**。

| 维度 | lead_agent | NarrationAgent（解说） |
|---|---|---|
| 装配入口 | `build_agent`（大而全） | `create_agent`（极简，新写薄封装） |
| checkpointer | 有（多轮记忆） | 无（无状态，一次性） |
| middleware 链 | 全链 | **不挂** |
| 工具 | 沙箱 + 技能 + 记忆 + 业务工具 | ~7 个只读工具（**绝不含 write_file/bash**） |
| system_prompt | persona + `<skill_index>` | SKILL.md 正文全文 |
| 生命周期 | 常驻，worker 逐 chunk 消费 | 一次性，工具内 `invoke` 跑完即弃 |

NarrationAgent 是 `generate_narration` 工具背后的一次性 ReAct 循环，不是 lead_agent 的子图节点，二者互不污染上下文。

## 三、"裁剪"裁在哪

- `build_agent` 是"大而全"装配，会塞入沙箱全套工具（含 `write_file`/`bash`）、memory、middleware、MCP、subagents——**NarrationAgent 全都不需要，其中 write_file/bash 还是雷**。
- 因此 NarrationAgent **不复用 `build_agent`，只复用底层原语** `create_agent` / `create_chat_model` / `load_skills`，自己写约 30 行精简装配。

```python
from langchain.agents import create_agent
from deerflow_simple.model import create_chat_model
from deerflow_simple.skills.loader import load_skills

def build_narration_agent(config, skills_dir, read_only_tools):
    model = create_chat_model(config)
    skill = next(s for s in load_skills(skills_dir) if s.name == "novel-narration-generator")
    return create_agent(
        model=model,
        tools=read_only_tools,     # 只有 ~7 只读工具
        system_prompt=skill.body,  # SKILL.md 全文即身份
        # 刻意不传：middleware / state_schema / checkpointer
    )
```

## 四、委派链路

```
用户 → lead_agent(create_agent #1, 有checkpointer)
      → generate_narration(@tool)
          → 纯 if/else 参数校验（task_type 枚举/必填矩阵，不花 token）
          → NarrationAgent(create_agent #2, 无checkpointer).invoke(payload)
          → 返回 {draft, chapter_bases, certainty, gaps}
      → 组织最终回复
```

`generate_narration` 通过框架 M0 改造（`build_agent` 加 `extra_tools` 参数）挂进 lead_agent。

## 五、skill 的两层复用（易混淆点）

同一个 skill 机制，在两个 agent 身上用法**相反**：

| 层 | 用哪套机制 | 原因 |
|---|---|---|
| **lead_agent** | 渐进加载（`<skill_index>` + `describe_skill` + `read_file`） | 面对多个技能，按需选择 |
| **NarrationAgent** | **直接注入** SKILL.md 全文，不走渐进加载 | 唯一身份且是"宪法"，不能让其自行决定是否读取 |

NarrationAgent 走渐进加载是**错误**做法——只会平白多两次工具调用、增加不确定性。

## 六、一句话总结

> **框架零改造；复用 `create_agent` 原语，不复用 `build_agent` 大而全装配；lead_agent 与解说 agent 是"两个 `create_agent` 实例 + 一个 `generate_narration` 工具边界"，不是子图嵌套；skill 分两层——lead_agent 渐进加载、解说 agent 直接注入。**
